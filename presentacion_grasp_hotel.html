Patrón 01 · Relacionado con HU-10 (Check-out)

1. Information Expert (Experto en Información)

¿Qué problema resuelve?

Asigna una responsabilidad a la clase que posee la información necesaria para cumplirla.

Aplicación en el Hotel

En el Check-out (HU-10), la clase Reserva conoce las noches hospedadas, el precio por noche y la lista de consumos, por lo que ella misma calcula el total.

public class Reserva {
    private int noches;
    private double precioPorNoche;
    private List<Consumo> consumos;

    // Reserva es la experta: posee todos los datos
    public double calcularTotalCuenta() {
        double totalEstadia = noches * precioPorNoche;
        double totalConsumos = 0;
        for (Consumo c : consumos) {
            totalConsumos += c.getSubtotal();
        }
        return totalEstadia + totalConsumos;
    }
}
Nota de orador: "En lugar de calcular el total en un controlador externo sacando los datos con getters, le damos el método a Reserva porque ella es la dueña de las noches, la tarifa y la lista de consumos."
Patrón 02 · Relacionado con HU-09 (Consumos)

2. Creator (Creador)

¿Qué problema resuelve?

Define quién debe instanciar un objeto: la clase A crea a B si A contiene, agrega o registra objetos B.

Aplicación en el Hotel

Al cargar un producto del minibar (HU-09), CuentaHabitacion almacena la colección de consumos, por lo tanto es la encargada de hacer el new Consumo(...).

public class CuentaHabitacion {
    private List<Consumo> consumos = new ArrayList<>();

    // Creator: CuentaHabitacion agrega a Consumo,
    // por lo tanto ella misma lo instancia.
    public void registrarConsumo(String item, int cant, double valor) {
        Consumo nuevo = new Consumo(item, cant, valor);
        this.consumos.add(nuevo);
    }
}
Nota de orador: "Aquí evitamos que la interfaz gráfica instancie objetos Consumo sueltos. Como CuentaHabitacion los agrupa en una lista, ella asume la responsabilidad de crearlos."
Patrón 03 · Relacionado con HU-08 (Check-in)

3. Controller (Controlador)

¿Qué problema resuelve?

Primer objeto detrás de la capa de interfaz de usuario (UI) que recibe y coordina un evento del sistema.

Aplicación en el Hotel

Cuando el recepcionista presiona "Confirmar Check-in" (HU-08), CheckInController valida que esté pagada y delega la activación al dominio.

public class CheckInController {
    private ReservaService reservaService;

    // Recibe el clic de la vista y coordina el caso de uso
    public String procesarEventoCheckIn(String idReserva) {
        Reserva r = reservaService.buscarPorId(idReserva);
        if (!r.getEstado().equals("Pagada")) {
            return "Error: Reserva no está Pagada.";
        }
        r.activarEstadia();
        return "Check-in registrado exitosamente.";
    }
}
Nota de orador: "El botón de la pantalla nunca modifica la base de datos directo. Llama al CheckInController, quien orquesta el flujo del caso de uso."
Patrón 04 · Relacionado con HU-05 (Notificaciones)

4. Low Coupling (Bajo Acoplamiento)

¿Qué problema resuelve?

Reduce las dependencias entre clases para que el cambio en un proveedor externo no obligue a reescribir la lógica del hotel.

Aplicación en el Hotel

ReservaService depende de la interfaz CanalNotificacion, permitiendo cambiar entre Email, WhatsApp o SMS sin tocar la reserva.

public interface CanalNotificacion {
    void enviarComprobante(String destino, String msg);
}

public class ReservaService {
    private CanalNotificacion notificador;

    public ReservaService(CanalNotificacion notificador) {
        this.notificador = notificador;
    }

    public void confirmarReserva(String email) {
        notificador.enviarComprobante(email, "Reserva confirmada");
    }
}
Nota de orador: "Gracias a la interfaz CanalNotificacion, ReservaService tiene bajo acoplamiento: no sabe si enviamos por Gmail, SMTP o WhatsApp."
Patrón 05 · Relacionado con HU-11 y HU-15 (Inventario)

5. High Cohesion (Alta Cohesión)

¿Qué problema resuelve?

Mantiene una clase enfocada en una única responsabilidad altamente relacionada, evitando clases gigantes difíciles de mantener.

Aplicación en el Hotel

La clase Habitacion solo administra sus transiciones de estado físico (Disponible, Ocupada, En Limpieza), sin mezclar cobros ni PDFs.

public class Habitacion {
    private String numero;
    private String estado;

    // Alta cohesión: solo gestiona el estado del cuarto
    public void ocupar() { this.estado = "Ocupada"; }
    public void enviarALimpieza() { this.estado = "En Limpieza"; }
    public void habilitarDisponible() { this.estado = "Disponible"; }
}
Nota de orador: "Habitacion hace una sola cosa y la hace bien: controlar su estado físico en el hotel."
Patrón 06 · Relacionado con HU-04 (Cancelaciones)

6. Polymorphism (Polimorfismo)

¿Qué problema resuelve?

Reemplaza condicionales complejos (if/else) por clases que implementan una misma interfaz según la regla de negocio.

Aplicación en el Hotel

En la cancelación (HU-04), si se cancela con más de 48h se devuelve el 100%; con menos de 48h se retiene el valor de una noche.

public interface PoliticaReembolso {
    double calcularReembolso(double total, double noche);
}

public class ReembolsoTotal implements PoliticaReembolso {
    public double calcularReembolso(double total, double noche) {
        return total; // > 48 horas
    }
}

public class ReembolsoConPenalidad implements PoliticaReembolso {
    public double calcularReembolso(double total, double noche) {
        return total - noche; // < 48 horas
    }
}
Nota de orador: "Si el hotel agrega mañana una tarifa No Reembolsable, solo creamos una nueva clase sin modificar las existentes."
Patrón 07 · Relacionado con HU-05 y HU-12 (PDF y QR)

7. Pure Fabrication (Fabricación Pura)

¿Qué problema resuelve?

Crea una clase técnica que no existe como objeto real del hotel para no degradar la cohesión de las entidades de negocio.

Aplicación en el Hotel

Ni Huesped ni Reserva deben saber renderizar binarios PDF ni códigos QR. Se inventa GeneradorPdfQR.

// Clase inventada puramente para soporte técnico
public class GeneradorPdfQR {
    public byte[] generarComprobante(String idReserva, String huesped) {
        String qr = "QR_DATA:" + idReserva;
        String pdf = "Reserva: " + idReserva + " | " + huesped + " | " + qr;
        return pdf.getBytes();
    }
}
Nota de orador: "En la vida real un hotel tiene recepcionistas y habitaciones, no tiene un 'GeneradorPdfQR'. Lo fabricamos para mantener limpia la clase Reserva."
Patrón 08 · Relacionado con HU-03 (Pagos PSE)

8. Indirection (Indirección)

¿Qué problema resuelve?

Introduce un objeto intermediario para que dos componentes (nuestro hotel y el banco externo) no se acoplen directamente.

Aplicación en el Hotel

AdaptadorPasarelaPSE traduce los datos de nuestra reserva al formato que exige la API bancaria externa (HU-03).

public class AdaptadorPasarelaPSE {
    private ApiExternaBancoPSE apiBanco;

    public String procesarPagoReserva(String idReserva, double monto) {
        boolean ok = apiBanco.ejecutarTransaccionBancaria(idReserva, monto);
        return ok ? "Aprobado" : "Rechazado";
    }
}
Nota de orador: "El adaptador actúa como intermediario para aislar nuestro dominio de la API externa de PSE."
Patrón 09 · Relacionado con HU-12 (Impuestos por Sede)

9. Protected Variations (Variaciones Protegidas)

¿Qué problema resuelve?

Identifica puntos que sabemos que van a cambiar por factores externos (leyes, impuestos) y los encapsula detrás de una interfaz estable.

Aplicación en el Hotel

Como el hotel es multi-sede, cada sucursal puede tener impuestos distintos (IVA 19%, exención turística). Factura queda protegida.

public interface CalculadoraImpuestoLocal {
    double calcularImpuesto(double subtotal);
}

public class Factura {
    private double subtotal;
    private CalculadoraImpuestoLocal reglaImpuesto;

    public double obtenerTotalConImpuestos() {
        return subtotal + reglaImpuesto.calcularImpuesto(subtotal);
    }
}
Nota de orador: "Si cambia el IVA o abrimos una sede en zona franca turística, la clase Factura no sufre ni una sola línea de modificación."
Síntesis para Preguntas del Profesor

Diferencia Clave: Low Coupling vs Indirection vs Protected Variations

Una pregunta clásica de evaluación en Diseño de Software es cómo distinguir estos tres patrones cuando todos usan interfaces:

1. Indirection (El Mecanismo)

Es la acción estructural de colocar un objeto intermediario (ej. AdaptadorPasarelaPSE) entre dos componentes.

2. Low Coupling (El Principio General)

Es la métrica de calidad que buscamos mantener en todo el sistema: que las clases tengan la menor cantidad de dependencias posibles.

3. Protected Variations (El Propósito Estratégico)

Es blindar deliberadamente un punto inestable del negocio (como leyes tributarias o pasarelas externas) para que sus cambios futuros no rompan el sistema.
